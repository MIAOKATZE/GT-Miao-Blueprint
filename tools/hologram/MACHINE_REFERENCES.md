# Native machine references

This optional tool makes visual references using GT5U's actual registered world renderers. It is independent of all hologram smoke suites and does not alter their assertions. Both helper classes live in the test source set; the two runtime entry points only load them when the dedicated reference property is enabled.

Run from the main checkout, using the same explicit support-jar directory accepted by `prepare_smoke.py`:

```powershell
python tools/hologram/prepare_smoke.py --mode reference --mods-source <support-jar-directory>
./gradlew.bat runServer -PhologramReferenceServer
python tools/hologram/prepare_client.py --mode reference
./gradlew.bat runClient -PhologramReferenceClient
```

The server uses a fresh empty `hologram-reference-*` world on localhost port 25582 under `build/hologram-reference/server`. It finds the controller by its exact registered class, captures its real StructureLib declaration, invokes its native `construct`, and substitutes service hatches only where the actual element declares that hatch. Six service hatches provide input/output buses, input/output fluid hatches, energy, and maintenance. Applicable machines also have an upward-facing muffler. The EBF muffler occupies the mandatory top-center element. Hatches use their actual machine casing texture after the native formation check.

Each machine must pass `checkStructure(true, base)` in the real server world before its full block metadata and native tile NBT are serialized. A failed machine prevents a server final PASS. No render snapshot is presented as formed without that check. The LCR constructor chooses exactly one heating coil, and service substitutions preserve it.

The current GT5U 5.09.54.205 controllers are:

The client reads the server snapshots into a detached read-only native world, creates fresh native tiles from saved NBT, restores every GT tile before rendering, and calls the original `IMetaTileEntity.onTextureUpdate()` client lifecycle callback only for the four audited controllers listed above. Hatches and unknown GT types receive no additional callbacks. It then calls `RenderBlocks.renderBlockByRenderType`. GT hatches, controllers, casings, coils, pipe casings, and frame boxes therefore use their registered renderers, actual textures, facing, and saved state. There is no schematic cube/material fallback, live-world connection, machine ticking, or invented block geometry.

The current industrial centrifuge is ID **15512**, not the legacy GT++ ID 790. Its nine-part turbine face comes from `MTEIndustrialCentrifuge.onTextureUpdate()` ? `GTUtilityClient.setTurbineOverlay()` ? GT's world-keyed `RenderOverlay` registry. The registered casing and full-block renderers consume that registry themselves. Loading NBT and asking only for the controller's ordinary `getTexture()` leaves a single center tile and is insufficient. The fixture keeps all eight casing support cells around the controller intact; its seven required service hatches occupy other legal structure positions. Client validation resolves each registered overlay's real `IIconTexture` atlas sprite and compares emitted north-face quads before and after the callback, separately for every accepted render pass. Each casing accepts pass 0 and gains one quad; native `BlockMachines.canRenderInPass` accepts both pass 0 and pass 1, so the center gains one quad in each pass. These are **9 distinct sprites and support faces, 36 unique geometry vertices, and 40 actually emitted overlay vertices**. The center's two native overlay quads must have identical coordinates and UV. Camera receipts explicitly distinguish `nativeOverlayUniqueVertices=36`, `nativeOverlayEmittedVertices=40`, and `nativeOverlayDuplicatePassVertices=4`; the legacy `nativeOverlayVertices` field is documented as a unique-geometry alias, never actual emission. `nativeOverlaySprites` contains nine cells with per-pass before/after counts, and `nativeOverlayPassGeometry` records all ten actual quads with sprite, pass, coordinates, and UV. The entire emitted mesh, including both center passes, is retained for solid and wireframe renders. Every reference scene releases the native overlay registry on exit or failure.

Sixteen PNGs appear under `build/hologram-reference/client/screenshots`: each machine gets `front-left`, `front-right`, `rear-left`, and `cutaway`. The first three views contain the complete formed structure. The fourth explicitly hides the front block plane in the detached render world to expose internal materials; it is labelled CUTAWAY and must not replace a complete-assembly reference. Machine renders must span at least 600 screenshot pixels in height, contain at least 30,000 visible material pixels, and retain at least 100 distinct material colors. The client also verifies actual native triangle emission and restored registered machine IDs.

All views use true perspective: vertical FOV **32°**, elevation **25°**, near/far planes **0.1/1000** blocks, and yaw from north **−35° / +35° / 145° / −35°**. The camera looks at the machine's bounding-box center with world +Y up. Distance is fitted against all eight actual bounding-box corners at 94% of the viewport; the viewport starts at `[80,90]` and is `[displayWidth−160, displayHeight−180]` pixels. Projection uses `glFrustum`, not GUI orthographic scaling. A `.camera.json` beside every PNG records projection, FOV, yaw, elevation, distance, target, viewport, clip planes, and native overlay counts. These values can be reused to keep an illustration's vanishing points consistent with its real machine references.

The same run also writes sixteen `*-comparison.png` files. Each is rendered directly in OpenGL as two viewports: native materials on the left and cyan blueprint wireframe on the right. The wireframe retains every quad position copied from the actual registered renderer's emitted tessellator buffer, uses `GL_LINE`, and preserves depth occlusion through an original native material depth pass. It draws no guessed cubes or reconstructed schematic geometry. Both panels share precisely the same perspective matrix, target, distance, and orientation; only their viewport origins differ. Comparison camera JSON records the narrower viewport and matching camera fit. The original sixteen solid screenshots still satisfy their full original material and size thresholds; comparison images have their own checks for material colors and visible cyan mesh. For an image-generation call limited to five inputs, use the original banner plus each machine's complete `front-left-comparison.png` reference.

Use the complete front views as image-generation references. Captions are reference annotations, not requested banner text. The LCR has one PTFE pipe casing and one heating coil, no glass or muffler; the electrolyzer has Potin frames and brass/tin pipe casings; the centrifuge has Eglin Steel frames and sieve grates. Additional decorative blocks would no longer match these structures.

Require `[GTMB-MACHINE-REFERENCE] FINAL PASS machines=4` and `[GTMB-MACHINE-REFERENCE-CLIENT] FINAL PASS screenshots=16 comparisons=16` in the logs. A failed fixture can shut down Minecraft while Gradle still exits successfully; the Gradle result alone does not verify the references.
