# 客户端原生预览驻留预算

本地作者预览的 **32 MiB 旧限制只针对已解码的原生方块/物品描述行**，不是 GTMB 全部内存，也不是整份蓝图的方块数限制。普通非 TileEntity 方块的精确方块/物品描述可直接显示，不一定进入这项预算。复杂机器、装饰模型和带 NBT 的物品通常更早消耗容量。

现在该项预算在打开作者文档时按 JVM 最大堆自动计算：

```
自动目标 = min(256 MiB, max(32 MiB, JVM 最大堆 / 32))
最终上限 = min(目标, 512 MiB, JVM 最大堆 / 8)
```

例如 `-Xmx5G` 的自动目标约为 **160 MiB**；`-Xmx2G` 为 **64 MiB**。这是保守的客户端资源分配策略，不代表已经测得所有模组/蓝图的最优值，也不保证一份巨型蓝图的所有原生细节能够同时驻留。

需要手动调整时，在启动器的 **JVM 参数**里添加：

```
-Dgtmb.preview.nativeResidentMiB=256
```

- 单位 MiB；省略、`0`、负数或无法解析的值使用自动策略。
- 正数按 8–512 MiB 范围约束，之后仍受最大堆的 1/8 限制；堆比例限制优先。
- 重启客户端后生效。配置不会更改蓝图文件、旧存档或网络协议。

这项预算与 Core 的进程级重工作业保留配额（`gtmb.heavy.retainedBytes`）、网络模型缓存、源文档、贴图、GL 显示列表及模组自身 TileEntity 内存相互独立，**不能将此数值视为 GTMB 的总堆/GPU 内存上限**。本次没有同步提高这些其他限制，也没有放宽正式蓝图格式或网络消息安全边界。

打开已保存成品时，为了让只移动相机后的普通保存保留原成品内容，运行时另持有一份有库文档大小上限的原始 JSON；这属于来源/保存状态，不计作已解码原生行，也不是全局无限缓存。

预览曾另设比正式蓝图更低的单格 NBT 限制，导致正式格式接受的大装饰/机器数据在本地变成“预览不可用”。现在作者预览与正式保存/截图的预览解码器都对齐已有正式格式：单份压缩及展开数据各最多 **8 MiB**、NBT 分配跟踪上限 **16 MiB**，保留深度、数组长度、类型与编码检查。正式保存/截图路径仍保留原有的 **64 MiB 累计展开数据上限**，重复引用仍累计，不因缓存去重而绕过。

作者路径沿用原有结构预检，在创建 NBT 树之前向 Core 非阻塞申请临时内存；同一格的 tile/item 两棵输入树累计计费，并另受当前作者驻留预算数值的工作区上限约束。该临时计费不是最终描述行大小；构造完拥有独立副本的行或失败后立即释放，最终行另按实际拥有数据计算驻留费用。Core 暂时繁忙会保留可恢复预算壳，已知需求在再次解压之前先重试准入，而不是被当作损坏数据或每帧重复解压。超过工作区上限的单格需要调整配置后重新打开，不能靠一直等待恢复。

这些是容量与准入限制，不是固定帧时保证：单格大型 NBT 的完整解码仍是客户端线程上的有界、不可中断操作，可能超过一次协作式时间片；后续格会让出时间，但没有把模组原生对象或 GL 工作擅自移到后台线程。

当可见原生行已占满预算时，预览保留已完成的可见结果，并显示预算不足的细节壳。对于已经确认无法容纳的需求，不会在固定视角下不断重扫淘汰候选；相机/层/依赖可见性变化或删除源格释放容量后，恢复有界重试。复杂模型的真实依赖保护依旧生效，不会把未知邻居当成不存在。放宽预算不能替代原生缓存失效和相机呈现生命周期的修复。
